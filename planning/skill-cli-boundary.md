# Whetstone skill, driver and kernel boundary

Whetstone turns an agreed project intent into verification that agents can
run and people can trust. Three layers do the work, and each owns a
different kind of truth. Keeping them apart stops judgment from being passed
off as enforcement, and keeps the `wh` binary small.

This contract follows the delegation plan (`planning/direction.md`, Beads
`whetstone-ppq`, adopted 2026-09-27). Where it describes code the plan
removes, that is marked below.

## The three layers

| Layer | Owns | Lives in |
| --- | --- | --- |
| Skill | Judgment: intent, relevance, repair, what a failure means | Agent host skill directories, generated by `wh init --action wire` |
| Driver | Driving the app (launch, doctor, steps, evidence, cleanup) and every network call, including Jev questions | `whetstone/verify/drive.mjs` and `driver.json`, owned by the team |
| Kernel | Determinism: records, state transitions, rule and gate execution, receipts | The `wh` binary and the private store |

## The skill owns judgment

The generated `verify-<app>` skill is a projection of accepted records. It
tells an agent why the project exists (mission and principles),
how to launch, doctor, drive and prove the app, what counts as evidence, which
rules are in force with their strength and enforcer, and which advisory rules
are red flags for designs and diffs.
The feature map inside it answers, per feature: what exists, how a person
reaches it, how to drive it, what proves it, what usually lies, and why it
exists.

The skill and map are written in pstack's verification-skill format
(`cursor/plugins/pstack`, skills `create-verification-skill` and
`maintain-verification-skill`). Each feature file carries YAML frontmatter with
Whetstone's fields (record id and revision, area, sweep order, why and serves,
constrained by, proven by, drift, entry points) and then exactly four H2s in
order: `Sub-features`, `How to get to it (user POV)`, `Driving it with
<harness>`, `Gotchas`. `features/README.md` follows pstack's shape: baseline
preconditions, driving conventions, proof and skip reporting, the feature entry
contract, then the features in sweep order. A skill pstack generated can be
imported with `wh init --action import`, and pstack's maintain skill runs on a
Whetstone-generated skill unchanged. The SKILL.md names pstack's `how`, `why`,
`blast-radius`, `interrogate`, `reflect` and `maintain-verification-skill` when
the plugin is installed, and tells the agent to brief itself with `how`, `why`
and `blast-radius` before building. Whetstone never reimplements those
judgment skills. Whetstone owns the format (a versioned schema, `whetstone-ppq.9.1`);
pstack's layout is its projection and import format.

Agents use the skill to decide what to change, which feature files apply,
whether a failure is doc drift, a harness gap or a product gap, and when to
stop and ask the owner. Asking is filing a Beads issue labelled `human` (the
owner sees it in `bd human list`) and taking other ready work. The triggers
are a must rule that is unknown or unavailable, a finding that survives a
second repair, a must-rule area, low Jev confidence, or a vague spec. Guidance and red flags are judgment, never a
deterministic pass. The skill never claims that delivering context, or a green
local run, proves authorization or a business outcome.

The skill is never edited by hand. People and agents change the records with
`wh change` (as private drafts the owner accepts), then regenerate the skill.
A stale projection is reported, not served silently. When pstack's maintain
pass edits the generated files, `wh init --action import --from <skill dir>`
returns exactly the edited features as private drafts with before/after, and
records nothing for files that still match; the same importer adopts a
skill pstack generated. Retiring a feature is `wh change --retire <id>`, a
reviewed draft that takes it out of force and out of the sweep while every
revision stays in history.

## The driver owns driving

The driver is a small, dependency-free script scaffolded once from a
repository interview and then owned by the team. It drives the real app the
way a user does, over the Chrome DevTools Protocol for web and desktop, a
process for command-line tools, or HTTP for services. It follows the
agent-friendly CLI bar: composable subcommands in pstack's control-adapter
vocabulary (`doctor`, `launch`, `drive`, `inspect`, `screenshot`, `cleanup`,
with `prove` as the composite `wh check` runs), `--dry-run` on anything with
side effects, machine-readable output, errors that say what to do instead,
rich `help`, instance isolation (a port derived from the checkout and a
private data directory, passed to the app as `{port}`/`PORT` and
`{data_dir}`/`WH_DATA_DIR`), and optional seed data through `launch.seed`.
Benny-style automations can call it as their control adapter; when
cursor-team-kit's `control-ui` or `control-cli` is present the skill may name
that instead. `doctor` answers whether an instance is worth driving,
including build freshness. A drive against a stale build or an unhealthy
instance is not evidence. Every step leaves evidence (screenshots,
transcripts) in the directory `wh check` provides, and cleanup stops only what
the driver started and removes only its scratch data; the evidence stays.
Each drive receipt binds the driver script and configuration digests, the
exact feature (map) revision it proved, the doctor verdict it followed and the
Git commit it ran at.

The kernel never absorbs driving. New surfaces, selectors and seed strategies
are team edits to the driver, not new Whetstone code.

## Rules and enforcers

A rule has one statement, a rationale, one strength (`must`, `should`,
`advisory`), labelled examples, a source (mission, principle, exemplar or
owner), and exactly one enforcer, chosen in this order:

1. **Mechanical**: native linter, formatter, AST query, test, validator,
   drive proof, design-token check or public-surface check. The kernel runs
   it with the gate rules below.
2. **Question**: a literal yes/no question for Jev (TypeSafe System One),
   defined by the rule's labelled examples. The kernel hands the question to
   the driver's `ask` command; the driver sends only the unit the question
   needs, after redaction, with the pinned model; the kernel records a
   receipt with the model, question digest, input digest, probability,
   confidence and a redaction marker. The API key stays in
   `TYPESAFE_API_KEY` and never reaches records, receipts or logs. No key or
   no network is `unavailable`. A local-only rule never calls Jev.
3. **Review**: pstack's `/interrogate` or a named person, recorded as an
   attestation receipt bound to the commit and rule revision.

A question answer can flag a rule but can never satisfy a must rule: a must
rule needs a mechanical pass, a proof receipt or a review attestation. New
question rules start in shadow mode, where answers are recorded but not
enforced, until `wh eval` measures their precision against accepted and
dismissed flags and the owner accepts a promotion draft. Demotions,
promotions and replacing a recurring question with a mechanical check are
drafts too; nothing changes force without an owner's acceptance.

Today's code implements mechanical enforcers on the earlier `Standard`
record (strength `may` stands for advisory). Rule record v2, questions,
review attestations and shadow mode are `whetstone-ppq.3.1`, `.3.5`, `.5.2`
to `.5.5`.

## The kernel owns determinism

`wh` validates typed records, computes content identities, resolves which
revision is in force versus pending versus withdrawn, renders stable JSON and
views, executes in-force gates, binds receipts to the exact gate revision,
workspace fingerprint and evidence digests, and manages local transactions.
Identical inputs produce identical results.

Gate execution is deliberately narrow: no shell (literal argv, `&&` chains
only), an allowlisted environment, a repository-scoped working directory, and
bounded time and output. A timeout, truncation, missing driver, failed doctor,
or a drive without evidence is unknown, never a pass. Draft gates never run.

## Storage

Records live in Beads (`src/beads.rs`, `bd` 1.1.2 or later). Each record
revision is one bead: agreement records are `record` beads, proposals,
reviews, decisions and retirements are `decision` beads, and receipts and
repair sessions are `receipt` beads, all labelled `whetstone`. The metadata
holds the typed body as ASCII-escaped canonical JSON (`wh_record`; Beads
re-sorts metadata objects and a raw U+2028 breaks its reads), the revision,
content digest, supersedes reference and idempotency key; a `supersedes`
dependency links consecutive revisions, and lifecycle is a `wh:lifecycle:*`
label kept in step with the kernel. The kernel validates every body and digest
on read and reports malformed or edited metadata with the bead id rather than
repairing it. One bead per revision (not per record id) is deliberate:
`bd history` does not carry metadata, an accepted revision and a pending draft
need separate lifecycle labels, and new revisions never collide as cell
conflicts on pull. In-force resolution, digests and the
draft-never-displaces-accepted invariant stay in the kernel; integrity is by
digest and `bd history`, which makes tampering visible rather than
impossible.

Drafts, receipts and personal experiments live in a private Beads database
under `.git/whetstone/` that never gets a remote: it is initialized and used
with Git discovery fenced off (`GIT_CEILING_DIRECTORIES`), because `bd init`
inside a repository whose origin carries Beads data would clone the team's
database and wire its remote. Accepted, shared records live in the
repository's Beads database. Nothing about policy is committed to the code
branch; the Beads remote is transport only (`refs/dolt/data` in the Git
remote today). Embedded Beads has no SQL, so every read or write is one `bd`
call (about half a second for a write), and multi-record writes are sequential
idempotent appends closed by a completion marker; repeating an interrupted
request resumes it. The `dolt` binary is not a requirement.

## Records, lifecycle and authority

A proposal, an acceptance, a check receipt, a flag decision (accepted or
dismissed) and a raised hand are different records. Recording a change creates
a private draft; nothing is in force until the owner explicitly accepts it. A
team reviews shared changes through its platform's branch protection (see
below). A draft never
displaces the accepted record. Every accepted change is append-only and linked
to what it supersedes; corrections are new records, not rewrites.

`wh push` shows the exact package (accepted revisions with the proposals and
reviews that accepted them), the destination and the base, and copies it into
the shared database and calls `bd dolt push` only with the matching
`--confirm` token; any change to package, destination or base invalidates the
token. A record whose revision chain holds a draft or withdrawn revision
carries private ancestry and is blocked unless that ancestry is explicitly
selected (`--include-ancestry`); a record linking to something unshared is
blocked until that is shared too; `--canary` text blocks a push outright.
`wh pull` calls `bd dolt pull`, verifies every incoming record and reports
arrivals and any collision with local drafts; it never executes, activates or
accepts incoming content, and local drafts are untouched. Local preferences
cannot weaken required team rules.

## Gates and team enforcement

Every tool commits and pushes through Git, so the gates sit there:

1. **Pre-commit**: `wh check --staged` runs mechanical enforcers on staged
   files only, within about two seconds, chaining any existing hook.
2. **Pre-push**: the full `wh check` for the commits being pushed:
   mechanical, questions (unless shadow or local-only), review attestations,
   and fresh proofs for features whose entry points changed.
3. **CI**: the same check as the required status `whetstone/policy`.

Independent review of shared rules is the platform's own branch protection
(required review, the required status, no force pushes). Whetstone keeps no
second trust root, no activation state machine and no authority file.
`wh init --action wire --hooks` installs the Git hooks and `--ci` the
workflow (`whetstone-ppq.6.1` to `.6.3`).

The pre-push hook checks exactly what is pushed. It passes each pushed commit
to `wh check --pushed`, which refuses (unknown, with the reason) when that
commit is not checked out or tracked files have uncommitted changes, so a
push of another branch, several refs at once or a tag on an older commit is
refused rather than vouched for; check it out and push it on its own.
Untracked files are not part of a push and never count. Command enforcers
(test, lint, validator) still run in the working tree, where an untracked
helper can influence them; CI, on a clean checkout, is the backstop. A review
attestation binds to the tracked content it reviewed (a Git tree), so it
holds at pre-commit and pre-push only while that content is unchanged.

The earlier PR-manifest activation model (ADR-0002, now
`planning/archive/trust-boundary.md`) has been removed: `wh push --propose`,
`wh change --activate`, `wh check --required`, `wh init --ci --reviewer`,
`.whetstone/authority.json`, gate exceptions, `src/authority.rs` and
`src/activation.rs`. Their records are still read, as retired kinds, and can
never be written again.

## Agent hosts

The same skill and map are written byte-identically into every selected host
(`.claude/skills`, `.cursor/skills`, `.agents/skills` for Codex and other
agents), stamped with the
agreement digest. Claude Code is hook-capable: `wh init --action wire --hooks`
adds a `SessionStart` hook (`wh dash --hook session-start`) that prints the
canonical context or says the skill is stale and must not be relied on (and
remembers the commit the session began at), and a `Stop` hook
(`wh check --hook stop`) that proves what changed since then, committed or
not, and returns violations to the same session for repair, bounded to three
returns before handing back to the owner; the third failure on the same key
raises a hand and lets the session stop. Codex gets the same loop through
`.codex/hooks.json` (`decision: block`) and Cursor through `.cursor/hooks.json`
(`followup_message`, loop limit three); the Claude hook skips input that
carries `cursor_version`, so Cursor never runs it twice. Other hosts use
explicit checkpoints (`wh check --changed --host <name>`). The Stop hook is the fast repair loop; the Git hooks
and CI are the enforcement. Each checkpoint records the skill
revision the host actually has; no checkpoint means not acknowledged, and a
projection that is stale, missing or hand-edited is reported per host, never
treated as delivered.

## Onboarding

`wh init` inspects the repository read-only, then walks the owner through the
agreement:

1. It detects Beads and pstack, and offers to install and pin them.
2. The owner states the mission.
3. The owner picks principles from pstack's catalogue or writes their own.
4. The owner optionally names exemplar codebases, which are read and never
   executed.
5. The owner accepts or skips three starter rules.
6. The skill proposes further rules as drafts, each with examples, strength,
   one enforcer and its source.

Nothing is in force until the owner accepts it. `--dry-run` shows the exact
records and writes nothing. From the terminal this is `--action setup`,
`--action agree --mission ... --principle ... --starter ...` and
`--action exemplar --from <path>|--url <url>`; the agreement is complete once
the mission and at least one rule are in force.

`wh init --action wire` interviews the repository (surface, launch, readiness,
isolation), scaffolds the driver once, and renders the skill, feature map and
journal into the chosen agent hosts, stamped with the agreement digest. The
first proof is one mapped feature driven end to end with evidence that
survives cleanup.

## Checking and maintenance

`wh check` runs every in-force gate. `--feature <id>` proves one feature
through its accepted drive steps; `--step <step>` (repeatable, one feature)
adds change-specific assertions that run after the accepted steps in the same
session, so a change is proven by what it changed and the receipt records
which steps were accepted and which were the change's own. The accepted steps
always run first; a change step can add to the proof, never replace it.
`--changed` runs the gates of features whose entry points cover changed files
(the working tree, plus everything since `--base <revision>` for committed
work) and reports which map entries may need review, and `--sweep` drives
every mapped feature in sweep order. `--dry-run` shows the selection and exact
commands without executing anything. Scanner rules delegated to a verified
linter binding (`lint_proxy`) are named in the scan summary as enforced by the
linter, not counted as missing evidence; any other skipped rule leaves the
scan unknown.

The map stays honest in two tiers. Incrementally, behaviour changes and their
feature edits ride the same change, and `wh check` reports drift when mapped
entry points changed after the last proof. Periodically, pstack's
`maintain-verification-skill` reads source per feature, drives every feature
live, and triages each difference as doc drift (fix the map), harness gap (fix
the driver) or product gap (file it, never paper over it in the map). Whetstone
owns only the deterministic half of that pass: the sweep with receipts, and
hygiene checks (features without steps or gates, dangling links, entry points
that match no files, README and file mismatches). Corrections return through
`wh change`; the maintain pass never edits product code.

## Public surface

Exactly six workflow families: `init`, `dash`, `change`, `check`, `pull` and
`push`. Bare `wh` is read-only orientation, and `--json` is the agent
interface. The dashboard and the CLI call the same typed services and return
the same records. The changelog also exports a show-me-your-work compatible TSV
(ts, phase, decision, why, evidence, result; one row per accepted change and
per receipt) so pstack's audit flow reads Whetstone's history directly:
`wh dash --trail`, `data.trail` with `--json`, or the dashboard's changelog
export (`/api/trail.tsv`).
